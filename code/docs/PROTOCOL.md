# Исследовательский протокол

Протокол основной конфигурации зафиксирован до открытия её тестовых метрик. Технический пилот использован для проверки работоспособности. Пилот и основной эксперимент не объединяются в статистическое сравнение.

## Вопрос и гипотеза

Может ли ограниченный автоматический поиск временных kernels улучшить CatBoost с содержательными ручными признаками при неизменных данных, кандидатах и модели?

Основное сравнение: `auto − manual` по macro end-to-end NDCG@10. Нулевая гипотеза — ожидаемое изменение равно нулю. Публикуются знак, абсолютная разность, относительное изменение и парный percentile bootstrap CI. Победа не является условием успешного исследования.

Поиск намеренно ограничен. Он выбирает окна/half-lives, но не изобретает новые типы отношений, SQL-программы или нейронные архитектуры. Все 15 колонок одного kernel входят в одну группу. Это делает бюджет и источник выигрыша интерпретируемыми.

## Популяция и estimand

Равномерно выбрать 10 000 уникальных пользователей исходной таблицы, seed 2026, сохранить все строки. Это не случайная выборка событий. Активность будущего не влияет на состав выборки.

В каждый срез ranking-метрики определены для тёплых пользователей с хотя бы одним будущим новым объектом. «Новый» означает отсутствующий в доступной реконструированной истории. Весь исходный KION дедуплицирован на уровне user–item, поэтому повторное потребление изучить нельзя. Пользователи без будущих целей не имеют определённой Recall/NDCG и исключены из estimand; холодные пользователи считаются отдельно. Для них не заявляется измеренное качество.

Сам генератор кандидатов не знает будущую активность. Он сначала обрабатывает всех тёплых пользователей. Выбор пользователей с измеримыми метками применяется после этого. Граф и item statistics строятся по истории всей user-выборки, включая пользователей без будущих целей.

## Разбиение

Полный архив заканчивается 22.08.2021. Конец данных трактуется как 23.08.2021 00:00, exclusive. Прогноз — семь дней.

| Срез | Начало | Конец exclusive | Использование |
| --- | --- | --- | --- |
| train_0 | 05.07.2021 | 12.07.2021 | Обучение |
| train_1 | 12.07.2021 | 19.07.2021 | Обучение |
| train_2 | 19.07.2021 | 26.07.2021 | Обучение |
| train_3 | 26.07.2021 | 02.08.2021 | Обучение |
| search | 02.08.2021 | 09.08.2021 | Глубина, деревья, выбор kernels |
| confirm | 09.08.2021 | 16.08.2021 | Независимая оценка выбранных рецептов |
| test | 16.08.2021 | 23.08.2021 | Единственная финальная оценка |

История `t < cutoff`; метки `cutoff <= t < end`. Обучающие метки предыдущего среза полностью известны к cutoff следующего, поэтому дополнительный gap при текущей недельной формулировке не нужен. Датасет не предоставляет задержек доставки событий: считаем запись доступной по её дате.

Неделя `search` используется многократно и подвержена winner's curse. Это допустимо для выбора рецепта, но её качество не служит доказательством улучшения. Confirm не участвует в принятии решений и не закрывает все риски обобщения: основной внешний контроль — test.

## Доступная информация и ограничения реконструкции

- `last_watch_dt` задаёт время доступности записи пары. Нельзя выдавать накопленные `total_dur`/`watched_pct` за прошлые значения; они исключены.
- Если последний просмотр в будущем, строка целиком скрыта прошлому срезу. Это может скрывать фактические ранние просмотры. Честно моделируем доступные записи, не восстанавливаем неизвестные события.
- Метаданные считаем статическими и известными; snapshot-версий нет. В признаки попадают только user/item текущего кандидата и категории исторических объектов.
- Каталог кандидатов включает только исторически наблюдавшиеся объекты в выбранной user-подвыборке. Новинки будущей недели не угадываются по наличию в полном CSV метаданных.
- В KION нет impression log: нулевая метка означает отсутствие наблюдавшейся цели в горизонте, не отказ после показа. Популяционные CTR и LogLoss не заявляются.

## Модель и поиск

Ручной baseline: CatBoostRanker, YetiRank mode NDCG top 10, CPU, learning rate 0,05, L2=5. Глубины 5/7, максимум 350 деревьев, оценка checkpoint через каждые 25. Основная метрика выбора учитывает unretrieved positives, а не только labels внутри Pool.

На одном seed 17 выбирается baseline, затем до двух шагов жадного добавления групп. Окна: 2, 3, 5, 10, 14, 21, 45, 60 дней. Экспоненциальные half-lives: 3, 10, 30 дней. Минимальный прирост для добавления — 0,0005 NDCG. Глубина auto наследуется от baseline, число деревьев выбирается отдельно. Пустой результат поиска валиден.

Контроли определены заранее: все kernels сразу и ручной baseline без косвенных агрегатов. Контроль «без косвенных агрегатов» сохраняет retrieval scores; его нельзя трактовать как удаление любой информации о жанрах. Seeds финального обучения: 17, 42, 73. Для каждого выполняется отдельный fit и считается отдельная метрика; итог — среднее метрик, не ансамбль.

После поиска все рецепты записываются в `frozen_recipe.json` и хешируются. Confirm обучается на train+search, test — на train+search+confirm. Параметры не корректируются по confirm. После открытия test любое исследование новых настроек требует нового внешнего периода или другого датасета.

## Метрики и неопределённость

Для пользователя u множество релевантных объектов R_u содержит все будущие novel targets, даже вне каталога/кандидатов. `Recall@K = hits@K / |R_u|`. Для бинарного NDCG `IDCG = sum(1/log2(r+1), r=1..min(K,|R_u|))`. MAP делится на `min(K,|R_u|)`. Пользователи без найденных релевантных кандидатов имеют ноль. Candidate recall и oracle NDCG показываются отдельно.

Bootstrap парный по user ID: усреднить метрики пользователя по model seeds, затем 3 000 resamples пользователей. RNG seed совпадает с `sample_seed`: 2026 для основного прогона и 2027 для репликации. Процентили 2,5/97,5%. Интервал описывает условную неопределённость разности на одной выборке и неделе. Общие item statistics и обучение не повторяются внутри resample; интервал не учитывает полный риск данных/обучения. Несколько model seeds не заменяют несколько user-sample seeds и внешних временных периодов.

Главное сравнение одно: auto vs manual. Интервалы контрольных абляций описательные. Нельзя выбирать лучший контроль по test и называть его подтверждённой основной гипотезой.

## Анализ и бюджет

Публикуются все search trials, confirm/test по каждому seed, средние, разброс seeds, доверительные интервалы, когорты по длине истории, candidate coverage, cold item targets, importance и абляции. Importance не является причинной атрибуцией.

Измеряются wall time каждого этапа и process RSS с периодом опроса 0,2 с. Основной прогон и репликация могут выполняться одновременно: значения времени описывают запуск в этой среде, а не изолированный hardware benchmark. Поиск дороже ручной настройки: до 21 отдельного trial добавления групп, плюс настройка baseline и контролей. Эта стоимость учитывается целиком. Код reference-level: item–item co-occurrence и потенциально плотные genre scores ограничивают масштаб. Экстраполяции на миллиарды событий без отдельного эксперимента нет.

Основной результат — выборка 10 000 пользователей, seed 2026. До открытия её test отдельно объявлена репликация на 10 000 пользователей с seed 2027, без изменения остальных параметров (`configs/replication.json`). В репликации заново выполняется та же процедура поиска: проверяется переносимость процедуры, не одного набора выбранных колонок. Результаты показываются раздельно; победителя между выборками не выбираем и CI двух выборок не объединяем. Период одинаковый, часть user ID может пересекаться, поэтому независимость репликаций не предполагается.

Следующие проверки должны заранее фиксировать новые размеры, внешние rolling-периоды или Yambda. На текущем test не продолжаем подбор после публикации результата.
